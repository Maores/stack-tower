# Hard Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a second difficulty mode that plays harder, keeps its own records and leaderboard, and describes every run in the terms of the mode it was played in.

**Architecture:** `core.js` gains a per-mode difficulty table and per-mode best keys, latched at run start and broadcast back out on `game:start` / `game:over`. `hud.js` owns the mode setting, the title switch, the unlock gate, and every mode-aware read. The two files couple only through window CustomEvents, exactly as `hud:world` already does. `visuals.js` and `audio.js` are not modified at all.

**Tech Stack:** Vanilla ES5 browser JS (no build step for the game itself), Three.js 0.149 via CDN, Supabase PostgREST, Playwright for tests, `scripts/build-offline.mjs` for the single-file offline build.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-08-02-hard-mode-design.md`. It governs; this plan implements it.
- `hud.js` is ES5 in style: `var` only, no arrow functions, no template literals, no `const`/`let`, IIFE-wrapped, defensive `try/catch` around every storage and event call, `/* */` comments. `core.js` and `visuals.js` use `//` comments and the same ES5 rules.
- **Never `innerHTML` for user data.** Every text node uses `textContent`. Existing `innerHTML` use is limited to hardcoded inline SVG and must stay that way.
- Cross-domain coupling goes through window CustomEvents only. Never call into another file's internals.
- Boot-time broadcasts gate on `DOMContentLoaded` behind a `readyState` guard, never a bare `setTimeout(0)`. Classic scripts stream on network loads and a queued timer can fire between their downloads.
- Game UI text stays English. Hebrew player names are data and keep their LRM guard in roast templates.
- The Supabase key in `hud.js` is the publishable key and is meant to be public. **Never put a service key anywhere in this repo.**
- Any test that can reach the save flow must intercept `**/rest/v1/stack_scores*` so no real rows land on the friends' board.
- Scripted runs need `?debug=1` in the URL. Without it `StackCore.debug` is a taunting decoy.
- `reference/` is gitignored. Test files written there are run evidence and are **not** committed. Commit steps list source files only.
- Difficulty values are final: normal `2.7 / 0.055 / 6.8 / regrow`, hard `3.8 / 0.100 / 9.0 / no regrow`.
- The Hard unlock gate is the Marble threshold (70) and must be **derived from the `TIERS` table by name**, never written as a second literal.
- Normal play must be bit-for-bit identical to what ships today.

## File Structure

| File | Responsibility in this feature |
|---|---|
| `core.js` | Difficulty table, active mode, per-mode best storage, mode echo on `game:start` / `game:over`, `hud:mode` listener |
| `hud.js` | Mode setting + persistence, unlock gate, title switch, mode-aware board reads/writes, lens death screen, records row, points multiplier |
| `hud.css` | Title chrome row (shop pill + switch), switch styling, locked state |
| `Stack.html` | Regenerated artifact, never hand-edited |
| `reference/tests/pw-hard-*.js` | New suites (gitignored run evidence) |

`visuals.js` and `audio.js` are untouched. The ghost line follows the active mode for free because it reads `StackCore.getTowerState().best` and `visuals.js` already calls `ghostSync()` on `game:start`.
